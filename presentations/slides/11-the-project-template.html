Block 1

What a template is

The idea first — it belongs to no language and no vendor.

Microsoft Web Technologies

The idea

A template is a project with the boring decisions already made

Not this

Copying a folder

The old project's name is baked into the folder, the project file, the namespaces and every using. Renaming it by hand is a long afternoon of find-and-replace, and it is easy to miss one.

Not this either

A library we install

A library is code we call and never see. A template is code we own from the moment it is created: every file is ours to read and change.

This

A blueprint the tool stamps out

We register it with our tooling once. From then on, one command produces a fresh, correctly named copy — as often as we like.

Every stack has this. dotnet new, npm create, django-admin startproject, rails new — the same idea with different spelling.
Microsoft Web Technologies

What is inside

Six things, already working

MVC

Controllers, views, layout

A home page, a shared layout and Bootstrap, exactly as in Sessions 03–06.

Identity

Login and registration

Real accounts, hashed passwords, an Admin role and one seeded administrator.

EF Core

SQLite or PostgreSQL

One setting in appsettings.json picks the provider — Sessions 07–08.

Repository

One data-access pattern

IRepository<T> registered for every entity at once, with no per-entity code.

Comments

Teaching code

Every file is commented in English and Bulgarian. It is meant to be read, not just run.

Rename

Our name everywhere

Folders, project file, solution and namespaces all take the name we pass in.

Microsoft Web Technologies

Honesty

And three things it deliberately does not do

No entities

The domain is empty

There is no Article, no Product, no Recipe. The subject of our project is the one thing the template cannot guess.

No migrations

The first one is ours

Migrations are tied to a database provider, so shipping one would force a choice on us. We create it after we have chosen.

No credentials

The admin fields are blank

A template with a default password in it is a template whose password is on every machine in the room. We fill ours in.

All three are one-off steps, and all three are on the next few slides.

Block 2 · demo

Installing it, and creating our project

Two commands to install. One command per project, forever after.

Microsoft Web Technologies

Before we start

Two things have to be on the machine

The .NET 10 SDK

The same one we installed in Session 02. Check it:

# prints the installed SDK version
dotnet --version
10.0.100

The EF Core command line tools

A global tool, installed once per machine. This is what creates migrations.

dotnet tool install --global dotnet-ef
Both are per-machine, not per-project. Once they are there, every project on this machine can use them.
Microsoft Web Technologies

Step 1 of 2 · once per machine

Clone the template and register it

# get the source
git clone https://github.com/eognianov/SimpleMVCTemplate.git

cd SimpleMVCTemplate

# register it with `dotnet new`
dotnet new install .

What that second command does

It reads .template.config/template.json and adds the template to the list dotnet new knows about. Nothing is compiled and nothing is copied yet.

Undo, and update

dotnet new uninstall . removes it. After a git pull, run dotnet new install . again to pick up the changes.

Microsoft Web Technologies

Step 2 of 2 · once per project

Stamp out a project with our own name

# anywhere OUTSIDE the cloned template folder
dotnet new simple-mvc -n MyName.MyApp

cd MyName.MyApp

simple-mvc

The template's short name, from template.json. dotnet new list shows it alongside mvc, console and the rest.

-n MyName.MyApp

The name of our project. Pick it once and pick it well — it becomes the namespace of every file.

Create it somewhere else on disk. The clone is the source of the template; our project is a separate folder with its own git history.

Block 3 · demo

The first run

Three steps between a fresh folder and a page we can log into.

Microsoft Web Technologies

First run · step 1

Fill in the administrator account

appsettings.json ships empty:

"Identity": {
  "Admin": {
    "Email": "",
    "Password": ""
  }
}

Before the first run, put real values in:

"Identity": {
  "Admin": {
    "Email": "admin@example.com",
    "Password": "Admin123!"
  }
}
If either field is blank the seeder does nothing — deliberately, because a deployed app may not want a seeded admin. The symptom is "no account exists and I cannot log in", with no error message anywhere.
Microsoft Web Technologies

First run · step 1, continued

The password has to satisfy the rules in Program.cs

.AddDefaultIdentity<ApplicationUser>(options =>
{
    options.SignIn.RequireConfirmedAccount = false;
    options.Password.RequiredLength        = 6;
    options.Password.RequireDigit          = true;
    options.Password.RequireUppercase      = false;
    options.Password.RequireNonAlphanumeric = false;
})

These are our rules

They are relaxed on purpose, so nobody loses twenty minutes to a rejected password. Tighten them for a real application.

They apply to everyone

Not just the seeded admin — the same rules validate every registration on the sign-up page.

If the seeder reports "could not create the admin user", the password we chose broke one of these lines.
Microsoft Web Technologies

First run · steps 2 and 3

Create the first migration, then run

# the INNER folder, next to the .csproj
cd MyName.MyApp

# step 2 — describe the schema
dotnet ef migrations add InitialCreate -o Data/Migrations

# step 3 — run it
dotnet run

Why a migration is needed at all

Identity brings its own tables — users, roles, logins, claims. Without a migration there is no schema, and start-up fails.

dotnet run does the rest

Start-up calls Database.Migrate() and then the seeder, so the database is created and the admin account exists before the first request is served.

First run · the result

A working site, before we have written a line

  • A home page and a privacy page on a shared Bootstrap layout.
  • Register and Log in in the navigation bar, both fully working.
  • An app.db SQLite file sitting next to the executable.
  • An Admin role, and one user in it — the address we just configured.
  • Password hashing, anti-forgery tokens and cookie sign-in, none of which we had to write.

Open the URL the console prints, and log in with the email and password from step 1.

A tour of the folders

Every folder has one job. Knowing which is which is most of finding our way around.

Microsoft Web Technologies

The map

What is where

MyName.MyApp/
├── MyName.MyApp.sln
└── MyName.MyApp/
    ├── Data/
    │   ├── AppDbContext.cs
    │   ├── DatabaseProviderSelector.cs
    │   ├── DesignTimeDbContextFactory.cs
    │   ├── DbSeeder.cs
    │   └── Migrations/         ← ours
    ├── Models/
    │   ├── BaseEntity.cs
    │   ├── ApplicationUser.cs

    ├── Areas/Identity/Pages/Account/
    ├── wwwroot/
    ├── appsettings.json
    └── Program.cs
  • Data/ — everything that talks to the database, including the Identity tables.
  • Models/ — our entities. BaseEntity gives each one an Id; ViewModels/ is for the shapes a view needs (Session 06).
  • Repositories/ — IRepository<T> and its implementation. The only door to the data.
  • Controllers/ and Views/ — Sessions 03 and 05, unchanged.
  • Areas/Identity/ — Login, Register and Logout as real files we can edit.
  • wwwroot/ — CSS, JavaScript, images: files the browser fetches directly.
Microsoft Web Technologies

The wiring

Program.cs is the whole configuration, on one screen

// the database, provider from appsettings.json
builder.Services.AddDbContext<AppDbContext>(o =>
    DatabaseProviderSelector.Configure(o, builder.Configuration));

// accounts, roles, and their storage
builder.Services
    .AddDefaultIdentity<ApplicationUser>(...)
    .AddRoles<IdentityRole>()
    .AddEntityFrameworkStores<AppDbContext>();

// ONE line covers every entity we will ever add
builder.Services.AddScoped(
    typeof(IRepository<>), typeof(Repository<>));

builder.Services.AddControllersWithViews();
builder.Services.AddRazorPages();

Registering, not calling

Each line teaches the container how to build something. Nothing runs yet — the container hands the object to whichever constructor asks for it, exactly as in Session 07.

The open generic

IRepository<> with nothing inside the angle brackets means any T. Add a tenth entity and there is still nothing to register.

Microsoft Web Technologies

Data/

Four files, four jobs

AppDbContext.cs

The database, as C#

It inherits IdentityDbContext<ApplicationUser>, so the users, roles and claims tables come with it. Our own DbSets go here.

DatabaseProviderSelector.cs

SQLite or PostgreSQL

Reads Database:Provider and configures the matching provider. One place, so nothing can disagree.

DesignTimeDbContextFactory.cs

For the tools

dotnet ef runs without starting the app, so it needs its own way to build a context. It calls the same selector.

DbSeeder.cs

The first data

Creates the Admin role and the admin user from configuration, on every start-up, and does nothing if they already exist.

Microsoft Web Technologies

A decision to make early

Which database — and why it is hard to change later

"Database": {
  "Provider": "Sqlite"     // or "PostgreSql"
},
"ConnectionStrings": {
  "Sqlite": "DataSource=app.db;Cache=Shared",
  "PostgreSql": "Host=localhost;Port=5432;..."
}

SQLite is the default

It works with no server, no installation and no password: the database is a file. Recommended unless our project genuinely needs more.

Migrations are provider-specific. A SQLite migration contains TEXT and INTEGER; a PostgreSQL one contains character varying and timestamp with time zone. They are not interchangeable.
# switching provider means starting the schema over
rm -rf Data/Migrations
dotnet ef migrations add InitialCreate -o Data/Migrations
dotnet ef database update

And the old database, with everything in it, is gone. Choose once, at the start.

Entity, then controller, then views. The same four steps for every feature we will ever add.

Microsoft Web Technologies

Step 1 · the entity

A class, a DbSet, a migration

// Models/Product.cs
namespace MyName.MyApp.Models;

public class Product : BaseEntity
{
    [Required]
    [MaxLength(100)]
    public string Name { get; set; } = string.Empty;

    public decimal Price { get; set; }
}
// Data/AppDbContext.cs
public DbSet<Product> Products => Set<Product>();
dotnet ef migrations add AddProduct -o Data/Migrations
dotnet ef database update

That is the whole registration

IRepository<Product> is now injectable. No line was added to Program.cs.

Microsoft Web Technologies

Why : BaseEntity

Four lines that make the generic repository possible

public abstract class BaseEntity
{
    public int Id { get; set; }
}
public interface IRepository<T>
    where T : BaseEntity

The constraint is the point

where T : BaseEntity promises the compiler that every T has an Id. Without that promise, GetById could not be written once for all entities.

abstract means "never on its own"

There is no such thing as a BaseEntity in the database. It exists only to be inherited.

Forgetting : BaseEntity is the usual reason IRepository<MyThing> refuses to compile.
Microsoft Web Technologies

Step 2 · the repository

Seven methods, and one of them is the one everybody forgets

MethodWhat it does
T? GetById(int id)The entity with that id, or null. The ? forces us to handle "not found".
IEnumerable<T> GetAll()Every row of that type.
Find(Expression<…>)The rows matching a condition — Find(p => p.Price < 10).
Add / Update / RemoveMark an entity as new, changed or deleted. Nothing reaches the database.
SaveChanges()Writes everything, in one transaction. Without it, nothing was saved.
Why Expression<Func<T,bool>> and not a plain Func? A plain delegate is compiled code EF Core cannot look inside, so it would load the whole table and filter in memory. An expression is a description of the condition, which EF Core translates into SQL WHERE — the filtering happens in the database.
Microsoft Web Technologies

The rule

A controller never touches AppDbContext

One

The controller stays small

No EF Core in it at all — just "get these, show this view".

Two

It can be tested

A test can hand it a fake repository, with no database anywhere.

Three

The rules live in one place

Change how data is fetched once, instead of in nine controllers.

If a controller has _context in it, something has gone wrong.

Microsoft Web Technologies

Step 3 · the controller

Ask for the repository; the container provides it

public class ProductController : Controller
{
    private readonly IRepository<Product> _products;

    // injected — we never call `new`
    public ProductController(IRepository<Product> products)
        => _products = products;

    // GET /Product
    public IActionResult Index()
        => View(_products.GetAll());

    // GET /Product/Details/5
    public IActionResult Details(int id)
    {
        var product = _products.GetById(id);
        return product is null ? NotFound() : View(product);
    }
}

Nine lines, no database code

The route ({controller}/{action}/{id?}, Session 04) and the container (Session 07) do the rest.

NotFound() is a 404

A missing id is the client's mistake, not ours — Session 01's 4xx versus 5xx, in one line.

Step 3, continued

The write half: validate, save, redirect

// POST /Product/Create
[HttpPost]
[ValidateAntiForgeryToken]
public IActionResult Create(Product product)
{
    if (!ModelState.IsValid)
    {
        return View(product);   // show the errors
    }

    _products.Add(product);
    _products.SaveChanges();       // or nothing happens
    return RedirectToAction(nameof(Index));
}

All three are from Session 09

ModelState.IsValid checks the annotations on the model; [ValidateAntiForgeryToken] blocks CSRF; the redirect stops a refresh from posting twice.

Add without SaveChanges is the single most common "my data disappeared".

When seven is not enough

Write a specific repository — and only then

// Repositories/IProductRepository.cs
public interface IProductRepository : IRepository<Product>
{
    IEnumerable<Product> GetCheaperThan(decimal price);
}

// Repositories/ProductRepository.cs
public class ProductRepository
    : Repository<Product>, IProductRepository
{
    public ProductRepository(AppDbContext c) : base(c) { }

    public IEnumerable<Product> GetCheaperThan(decimal price)
        => DbSet.Where(p => p.Price < price)
                .OrderBy(p => p.Price)
                .ToList();
}

// Program.cs — this one DOES need registering
builder.Services.AddScoped<IProductRepository,
                          ProductRepository>();

Usually we do not need one

The open-generic registration already covers every entity. Add a specific repository only for a query the seven methods cannot express — loading related data with Include, for example.

Inherit, do not replace

Inheriting Repository<Product> keeps all seven methods. DbSet and Context are protected, so they are ours to use.

Using the accounts we were given

Two attributes, and the site has private areas

[Authorize]                    // any signed-in user
public class ProductController : Controller
[Authorize(Roles = "Admin")]   // administrators only
public class AdminController : Controller
[AllowAnonymous]               // an exception, on one action
public IActionResult Index() => View();

Where the check happens

Before our action runs. An anonymous visitor is sent to the login page; a signed-in user without the role gets access denied.

The Admin role already exists

The seeder created it on first start-up, with our account in it. Nothing else to set up.

Views can ask too: User.Identity.IsAuthenticated and User.IsInRole("Admin") decide whether a button is even drawn.

Our own project

What to build, how big to make it, and the two rules that are not negotiable.

Microsoft Web Technologies

The whole path

From empty folder to our own application

  1. Clone the template, dotnet new install . — once per machine.
  2. dotnet new simple-mvc -n MyName.MyApp.
  3. Fill in the admin email and password.
  4. Choose the provider. SQLite unless there is a reason.
  5. Write the entities of our domain, each : BaseEntity.
  1. Add a DbSet per entity, then the migration.
  2. A controller per entity, taking IRepository<T>.
  3. The five views, on the layout that is already there.
  4. [Authorize] where the site should be private.
  5. git init, commit, and push — with no secrets in it.
Steps 5 to 8 repeat for every entity. Everything before them happens exactly once.
Microsoft Web Technologies

Choosing a subject

Small domain, complete application

Right size

Two or three entities

A recipe book. A film catalogue. A team roster. A reading list. Something whose rules we can explain in one sentence.

What is graded

That it works end to end

Create, list, view, edit and delete, with validation that actually rejects bad input, and pages that are private when they should be.

What sinks projects

Ambition without a first migration

Nine entities and a payment gateway, none of it running. One entity that works beats five that do not.

Start with one entity, end to end, on day one. Add the second only once the first is complete.
Microsoft Web Technologies

Not negotiable

Two rules about what goes into git

Rule one

No real credentials, ever

For coursework, an admin password and a connection string in appsettings.json are fine. A real password pushed to GitHub is public within seconds and stays in the history after it is deleted.

Real applications keep them in user-secrets or environment variables.

Rule two

No bin/, obj/ or *.db

They are build output and data — regenerated on any machine, and useless in a repository. The template's .gitignore already covers all three.

Commit the migration files, though: they are source.
